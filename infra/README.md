# Infrastructure

Terraform for running Squared on AWS: Fargate behind an ALB, Postgres on RDS, secrets in Secrets Manager.

> **Validated, not yet applied.** `terraform fmt -check` and `terraform validate` both pass against the AWS provider. It has never run against a real account, so quota limits, certificate validation timing, and RDS parameter compatibility stay unproven until a first `plan`.

## Shape

```
              Internet
                 │  HTTPS (443) — HTTP is 301-redirected
                 ▼
        ┌──────────────────┐
        │       ALB        │   public subnets, 2 AZs
        └────────┬─────────┘
                 │  :3000, from the ALB security group only
                 ▼
        ┌──────────────────┐
        │  Fargate tasks   │   public or private subnets — see below
        └────────┬─────────┘
                 │  :5432, from the task security group only
                 ▼
        ┌──────────────────┐
        │   RDS Postgres   │   private subnets, encrypted, TLS enforced,
        └──────────────────┘   no public access, no internet route
```

Each tier accepts traffic only from the tier in front of it, expressed as security-group references rather than CIDR ranges, so the rules stay correct as addresses change.

### Where the tasks run: `use_nat_gateway`

A NAT gateway costs about **$32/month before data charges** — the largest single line item in this stack — and what it buys is network topology, not access control.

**`false` (default).** Tasks run in public subnets with a public IP. Inbound is still restricted by security group to the load balancer alone, so nothing on the internet can open a connection to them; the public IP exists only so they can call Stripe and pull images. The database stays private and unreachable either way.

**`true`.** Tasks run in private subnets and reach the internet through a NAT gateway. This is the topology to run with real money moving through it — a compromised task can't be addressed directly even if a security group is later misconfigured, and outbound traffic leaves from a stable IP that an upstream provider can allowlist.

Both paths are in the code because the trade-off, not the default, is the point.

## Cost

With the defaults — no NAT gateway, one task at 0.25 vCPU / 0.5 GB — roughly **$20–30/month** in us-east-1, and lower if free-tier allowances cover the ALB and RDS:

| Component | Default | With `use_nat_gateway = true` |
|---|---|---|
| NAT gateway | — | ~$32 |
| ALB | ~$16 | ~$16 |
| Fargate | ~$9 (1 × 0.25 vCPU) | ~$30 (2 × 0.5 vCPU) |
| RDS `db.t4g.micro` | ~$12 | ~$12 |
| Secrets Manager (5) | ~$2 | ~$2 |
| **Total** | **~$40, less free tier** | **~$92** |

Free-tier coverage depends on account age — AWS moved new accounts to a credits model in mid-2025, so check your own account rather than assuming the old twelve-month allowances.

A budget alarm is provisioned as part of the stack: it emails `alert_email` at 80% of `monthly_budget_usd` on actual spend, and again when the month is forecast to exceed it.

## Secrets

`DATABASE_URL`, `JWT_SECRET`, `STRIPE_SECRET_KEY`, and `STRIPE_WEBHOOK_SECRET` live in Secrets Manager and are injected by the ECS agent at task start through the task definition's `secrets` field. They never appear in the task definition, the console, environment files, or this repository. The execution role can read exactly those secret ARNs — no wildcards.

Database and JWT secrets are generated by Terraform. **Stripe keys are created as empty secrets and populated out of band**, so live keys never enter Terraform state.

## Deploying

### 1. Remote state

Uncomment the `backend "s3"` block in `main.tf` and create the bucket first. State holds database endpoints and secret ARNs, so it does not belong on a laptop.

### 2. Create the registry, then push an image

The ECS service refers to an image by tag, so the registry has to exist and hold that tag before the rest of the stack comes up. Create it alone first:

```bash
cd infra
terraform init
terraform apply -target=aws_ecr_repository.app -var="image_tag=unused" -var="alert_email=you@example.com"
```

```bash
cd ..
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REPO="$ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/squared"
TAG=$(git rev-parse --short HEAD)

aws ecr get-login-password | docker login --username AWS --password-stdin "$REPO"
docker build --platform linux/amd64 -t "$REPO:$TAG" .
docker push "$REPO:$TAG"
```

`--platform linux/amd64` matters on Apple Silicon: the task definition requests `X86_64`, and an arm64 image starts and immediately dies with an exec-format error.

### 3. Apply the rest

```bash
cd infra
terraform apply \
  -var="image_tag=$TAG" \
  -var="alert_email=you@example.com" \
  -var="route53_zone_id=Z0123456789ABCDEFGHIJ"   # omit if DNS is elsewhere
```

Certificate validation blocks until ACM sees the DNS record. With the zone in Route 53 that resolves automatically in a minute or two. **If DNS lives elsewhere**, apply the certificate alone first, read the records out, add them at your provider, then apply the rest:

```bash
terraform apply -target=aws_acm_certificate.main -var=...
terraform output acm_validation_records
# add the CNAME at your DNS provider, then re-run the full apply
```

### 4. Migrate

The app comes up healthy before this runs — the health check is `SELECT 1`, which succeeds against an empty database — but real requests fail until the tables exist, so migrate right after the first apply.

```bash
terraform output -raw run_migration_command   # copy-paste ready
```

On later deploys, migrate *before* applying the new image tag.

Migrations run as their own one-off task rather than at app startup. With several tasks starting at once, migrating at boot means every task races to apply the same DDL; as a separate step the deploy fails loudly on a bad migration instead of half-migrating under load.

### 5. Stripe

Register `https://<app_domain>/api/stripe/webhook` in the Stripe dashboard, then store the signing secret it returns:

```bash
aws secretsmanager put-secret-value \
  --secret-id squared/stripe-secret-key --secret-string 'sk_test_...'
aws secretsmanager put-secret-value \
  --secret-id squared/stripe-webhook-secret --secret-string 'whsec_...'
aws ecs update-service --cluster squared --service squared --force-new-deployment
```

The last command is needed because secrets are read at task start — an updated secret reaches the app only on the next deployment.

## Deliberate choices

**The health check queries the database.** `/api/health` runs `SELECT 1`, so a task that can't reach Postgres is pulled from rotation and replaced rather than serving errors that look healthy at the process level. With the deployment circuit breaker, a broken revision rolls itself back.

**Image tags are immutable and never `latest`.** ECR rejects overwriting a tag, so a deployed SHA always refers to exactly one image.

**Single-AZ RDS.** Halves the database cost and is the first thing to change for real users.

## Teardown

`deletion_protection` is on for both the ALB and RDS, so `terraform destroy` fails until both are disabled deliberately — the guardrail exists precisely so an accidental destroy of a database holding payment records doesn't succeed.

```bash
terraform apply -var="..." \
  -var-file=... # after setting deletion_protection = false on both resources
terraform destroy -var="..."
```

Budget alarms and the ECR repository survive independently; delete them by hand if the account is being retired.
