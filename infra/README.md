# Infrastructure

Terraform for running Squared on AWS: Fargate behind an ALB, Postgres on RDS, secrets in Secrets Manager.

> **Validated, not yet applied.** `terraform fmt -check` and `terraform validate` both pass against the AWS provider, so the configuration is syntactically and semantically well-formed. It has never been applied to a real account, so runtime concerns — quota limits, ACM certificate validation, RDS parameter compatibility — remain unproven until a first `terraform plan` runs against live credentials.

## Shape

```
              Internet
                 │  HTTPS (443) — HTTP is 301-redirected
                 ▼
        ┌──────────────────┐
        │       ALB        │   public subnets, 2 AZs
        └────────┬─────────┘
                 │  :3000, from the ALB security group only
                 ▼
        ┌──────────────────┐        ┌──────────────────┐
        │  Fargate tasks   │───────▶│  NAT ── Stripe   │  HTTPS egress only
        │  private subnets │        └──────────────────┘
        └────────┬─────────┘
                 │  :5432, from the task security group only
                 ▼
        ┌──────────────────┐
        │   RDS Postgres   │   private, encrypted, TLS enforced, no public access
        └──────────────────┘
```

Each tier accepts traffic only from the tier in front of it, expressed as security-group references rather than CIDR ranges, so the rules stay correct as addresses change.

## Secrets

`DATABASE_URL`, `JWT_SECRET`, `STRIPE_SECRET_KEY`, and `STRIPE_WEBHOOK_SECRET` are stored in Secrets Manager and injected by the ECS agent at task start via the task definition's `secrets` field. They never appear in the task definition, the console, environment files, or this repository. The execution role can read exactly those secret ARNs — no wildcards.

The database and JWT secrets are generated by Terraform. **Stripe keys are created as empty secrets and populated out of band**, so live keys never enter Terraform state:

```bash
aws secretsmanager put-secret-value \
  --secret-id squared/stripe-secret-key --secret-string 'sk_live_...'
aws secretsmanager put-secret-value \
  --secret-id squared/stripe-webhook-secret --secret-string 'whsec_...'
```

## First deploy

Prerequisites: a Route 53 domain, an ACM certificate for it in the same region, and the Terraform state backend uncommented in `main.tf`.

```bash
cd infra
terraform init
terraform apply -var="app_domain=squared.example.com" \
                -var="acm_certificate_arn=arn:aws:acm:..." \
                -var="image_tag=<git-sha>"
```

Then build and push the image, run migrations, and roll out:

```bash
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REPO="$ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/squared"
TAG=$(git rev-parse --short HEAD)

aws ecr get-login-password | docker login --username AWS --password-stdin "$REPO"
docker build --platform linux/amd64 -t "$REPO:$TAG" .
docker push "$REPO:$TAG"

# Migrations run once, as their own task, before the new revision rolls out.
aws ecs run-task --cluster squared --task-definition squared-migrate \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[<private-subnet-ids>],securityGroups=[<app-sg-id>]}"

terraform apply -var="image_tag=$TAG" ...
```

Point the domain's DNS at the `alb_dns_name` output, then register `https://<domain>/api/stripe/webhook` in the Stripe dashboard and store the resulting signing secret.

## Deliberate choices

**Migrations are a separate one-off task, not an app-startup step.** With several tasks starting at once, running migrations at boot means every task races to apply the same DDL. As a distinct task the deploy fails loudly on a bad migration instead of half-migrating under load.

**The health check queries the database.** `/api/health` runs `SELECT 1`, so a task that can't reach Postgres is pulled from rotation and replaced, rather than serving errors that look healthy at the process level. Combined with the deployment circuit breaker, a broken revision rolls back on its own.

**Image tags are immutable and never `latest`.** ECR rejects overwriting a tag, so a deployed SHA always refers to exactly one image.

**Single NAT gateway.** ~$32/month each, so one serves both AZs. Losing it blocks outbound Stripe calls but not inbound traffic or the database. Two would be the call once settlements carry real money.

**Single-AZ RDS.** Halves the database cost. Multi-AZ is the first thing to change for real users — see the "at scale" notes in the root README.

## Cost

Roughly **$70–95/month** at idle in us-east-1: NAT gateway ~$32 plus data, ALB ~$16 plus LCUs, two Fargate tasks at 0.5 vCPU/1 GB ~$30, RDS db.t4g.micro ~$12, and a few dollars for logs, storage, and Secrets Manager. Scaling to zero isn't possible with this shape; a demo that must be cheap would run one task and drop the NAT by moving tasks to public subnets with tightened egress.

## Teardown

`deletion_protection` is on for both the ALB and RDS, so `terraform destroy` fails until both are disabled deliberately. That is intentional — the guardrail exists precisely so an accidental destroy of a database holding payment records doesn't succeed.
