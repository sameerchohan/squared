# Infrastructure

Terraform for running Squared on AWS: Fargate behind an ALB, Postgres on RDS, secrets in Secrets Manager.

> **Applied, verified, and destroyed on 31 August 2026.** This stack was deployed to a real AWS account, served the application over HTTPS at a domain with an ACM certificate, ran migrations, processed a Stripe webhook, and was then torn down. Total cost: about **$0.09**. The permanent demo stays on Vercel, for the reasons in the main README.
>
> Every pull request still runs `fmt -check`, `validate`, and a full `terraform plan` against the live account. That is real evidence — it confirms credentials, parameter validity, and quota headroom — and applying it drew the boundary of what it can confirm. Five clean plans preceded an apply that failed six times in twenty minutes, because a plan cannot evaluate string encoding rules, account entitlements, or certificate trust chains: none of them are consulted until a create call is made. All six are written up in the [engineering log](../docs/ENGINEERING-LOG.md), entries 16 to 21.
>
> `terraform plan` against the deployed stack reported **No changes**, which is the claim worth making. Convergence is stronger evidence than a creation count.

## Shape

```
              Internet
                 │  HTTPS (443) — HTTP is 301-redirected
                 ▼
        ┌──────────────────┐
        │       ALB        │   public subnets, 2 AZs
        └────────┬─────────┘
                 │  :3000, from the ALB security group only
                 ▼
        ┌──────────────────┐
        │  Fargate tasks   │   public or private subnets — see below
        └────────┬─────────┘
                 │  :5432, from the task security group only
                 ▼
        ┌──────────────────┐
        │   RDS Postgres   │   private subnets, encrypted, TLS enforced,
        └──────────────────┘   no public access, no internet route
```

Each tier accepts traffic only from the tier in front of it, expressed as security-group references rather than CIDR ranges, so the rules stay correct as addresses change.

### Where the tasks run: `use_nat_gateway`

A NAT gateway costs about **$32/month before data charges** — the largest single line item in this stack — and what it buys is network topology, not access control.

**`false` (default).** Tasks run in public subnets with a public IP. Inbound is still restricted by security group to the load balancer alone, so nothing on the internet can open a connection to them; the public IP exists only so they can call Stripe and pull images. The database stays private and unreachable either way.

**`true`.** Tasks run in private subnets and reach the internet through a NAT gateway. This is the topology to run with real money moving through it — a compromised task can't be addressed directly even if a security group is later misconfigured, and outbound traffic leaves from a stable IP that an upstream provider can allowlist.

Both paths are in the code because the trade-off, not the default, is the point.

## Cost

Defaults are tuned to be cheap: no NAT gateway, one task at 0.25 vCPU / 0.5 GB, single-AZ database. Charges are hourly, which matters more than the monthly figure — see [Teardown](#teardown).

| Component | Default | With `use_nat_gateway = true` |
|---|---|---|
| NAT gateway | — | ~$32 |
| ALB | ~$16 | ~$16 |
| Fargate | ~$9 (1 × 0.25 vCPU) | ~$30 (2 × 0.5 vCPU) |
| RDS `db.t4g.micro` + 20 GB | ~$14 | ~$14 |
| Secrets Manager (5) | ~$2 | ~$2 |
| Logs, ECR | ~$1 | ~$1 |
| **Total / month** | **~$42** | **~$95** |
| **Total / hour** | **~$0.057** | **~$0.13** |

Free-tier coverage depends on account age — AWS moved new accounts to a credits model in mid-2025 — and signup credits typically cover several months outright. Check the account's Credits page rather than assuming.

A budget alarm ships with the stack: it emails `alert_email` at 80% of `monthly_budget_usd` on actual spend, and again when the month is forecast to exceed it.

## Secrets

`DATABASE_URL`, `JWT_SECRET`, `STRIPE_SECRET_KEY`, and `STRIPE_WEBHOOK_SECRET` live in Secrets Manager and are injected by the ECS agent at task start through the task definition's `secrets` field. They never appear in the task definition, the console, environment files, or this repository. The execution role can read exactly those secret ARNs — no wildcards.

Database and JWT secrets are generated by Terraform. **Stripe keys are created as empty secrets and populated out of band**, so live keys never enter Terraform state.

## Deploying

### 0. Settings

Copy `terraform.tfvars.example` to `terraform.tfvars` and fill it in — region, domain, and the address budget alerts go to. It is gitignored, and having it means no `-var` flags below.

### 1. Remote state

Uncomment the `backend "s3"` block in `main.tf` and create the bucket first. State holds the database endpoint and secret ARNs, so it does not belong on a laptop.

### 2. Create the registry, then push an image

The ECS service refers to an image by tag, so the registry has to exist and hold that tag before the rest of the stack comes up. Create it alone first:

```bash
cd infra
terraform init
terraform apply -target=aws_ecr_repository.app -var="image_tag=unused"
```

```bash
cd ..
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REPO="$ACCOUNT.dkr.ecr.$(aws configure get region).amazonaws.com/squared"
TAG=$(git rev-parse --short HEAD)

aws ecr get-login-password | docker login --username AWS --password-stdin "$REPO"
docker build --platform linux/amd64 -t "$REPO:$TAG" .
docker push "$REPO:$TAG"
```

`--platform linux/amd64` matters on Apple Silicon: the task definition requests `X86_64`, and an arm64 image starts and immediately dies with an exec-format error.

### 3. Apply the rest

```bash
cd infra
terraform apply -var="image_tag=$TAG"
```

Certificate validation blocks until ACM sees the DNS record. With the zone in Route 53 that resolves automatically in a minute or two. **If DNS lives elsewhere**, apply the certificate alone first, read the records out, add them at your provider, then apply the rest:

```bash
terraform apply -target=aws_acm_certificate.main
terraform output acm_validation_records
# add the CNAME at your DNS provider, then re-run the full apply
```

#### Adding the records in Cloudflare

This project's domain is registered at Cloudflare with the apex and `www` pointing to Vercel. A subdomain for the app is purely additive — those two records are untouched, and the portfolio site keeps serving normally.

Two records are needed, both added under **DNS → Records**:

| Name | Type | Content | Proxy |
|---|---|---|---|
| `_<hash>.squared` | CNAME | `<value>.acm-validations.aws` | DNS only |
| `squared` | CNAME | the `alb_dns_name` output | DNS only |

The first comes from `terraform output acm_validation_records`; Cloudflare can't proxy underscore-prefixed records, so it stays DNS-only on its own. The second is the one to be careful with.

**Pick a name that does not already point at another platform.** ACM will refuse to issue for a hostname whose CAA policy excludes Amazon, and **CAA lookups follow CNAMEs** — so a name currently aliased to Vercel inherits Vercel's list of permitted authorities, which does not include Amazon. The apply fails with `FailureReason: CAA_ERROR` even though the DNS validation record is correct and ACM reports it as `SUCCESS`. There is no way to override it at that name: a CNAME cannot carry its own CAA records.

A sibling hostname avoids the problem entirely and leaves the existing site untouched. This deployment used `aws-squared`, whose CAA path is unrestricted to the root. Check before applying:

```bash
dig +short <the-name-you-want> CAA   # anything here that omits amazon.com will block ACM
```

Note that a *child* of the aliased name is no escape — `aws.squared.example.com` climbs through `squared.example.com` and inherits the same policy. Full write-up in the [engineering log](../docs/ENGINEERING-LOG.md), entry 16.

**Set it to "DNS only" (grey cloud).** If you turn the orange cloud on, Cloudflare terminates TLS itself and reconnects to the ALB, which is fine only if the zone's **SSL/TLS mode is "Full (strict)"**. On the default **"Flexible"** mode, Cloudflare speaks plain HTTP to the ALB, the ALB's listener answers with its 301 to HTTPS, Cloudflare follows it back to itself, and the site dies in an **infinite redirect loop**. Grey cloud avoids the whole question. If you later want Cloudflare in front for DDoS protection, switch the zone to Full (strict) first, then enable the proxy.

One consequence of grey cloud: the ALB's hostname is publicly visible, which is normal and not a security problem — inbound is still only 80 and 443, and the tasks behind it accept traffic solely from the ALB's security group.

### 4. Migrate

The app comes up healthy before this runs — the health check is `SELECT 1`, which succeeds against an empty database — but real requests fail until the tables exist, so migrate right after the first apply.

```bash
terraform output -raw run_migration_command   # copy-paste ready
```

On later deploys, migrate *before* applying the new image tag.

Migrations run as their own one-off task rather than at app startup. With several tasks starting at once, migrating at boot means every task races to apply the same DDL; as a separate step the deploy fails loudly on a bad migration instead of half-migrating under load.

### 5. Stripe

Register `https://<app_domain>/api/stripe/webhook` in the Stripe dashboard, then store the signing secret it returns:

```bash
aws secretsmanager put-secret-value \
  --secret-id squared/stripe-secret-key --secret-string 'sk_test_...'
aws secretsmanager put-secret-value \
  --secret-id squared/stripe-webhook-secret --secret-string 'whsec_...'
aws ecs update-service --cluster squared --service squared --force-new-deployment
```

The last command is needed because secrets are read at task start — an updated secret reaches the app only on the next deployment.

## Deliberate choices

**The health check queries the database.** `/api/health` runs `SELECT 1`, so a task that can't reach Postgres is pulled from rotation and replaced rather than serving errors that look healthy at the process level. With the deployment circuit breaker, a broken revision rolls itself back.

**Image tags are immutable and never `latest`.** ECR rejects overwriting a tag, so a deployed SHA always refers to exactly one image.

**Single-AZ RDS.** Halves the database cost and is the first thing to change for real users.

## Teardown

`enable_deletion_protection` defaults to **false**, so a demo deployment tears down cleanly:

```bash
terraform destroy
```

That removes everything billable in one step — no final snapshot left behind, and secrets are deleted immediately rather than sitting in a seven-day recovery window that blocks re-creating the same names on the next deploy.

Set `enable_deletion_protection = true` for anything real. It turns on deletion protection for the ALB and the database, takes a final snapshot on destroy, and gives deleted secrets a recovery window — at which point `terraform destroy` will refuse until the flags are deliberately flipped back. That refusal is the point: a database holding payment records should not be one command away from gone.

**The ECR repository and the budget alarm do not survive a destroy on their own.** Both live in this stack's state with nothing protecting them, so `terraform destroy` deletes them — and it will *fail partway through* while doing it, because `aws_ecr_repository` has no `force_delete` and the repository holds images:

```
RepositoryNotEmptyException
```

That aborts the teardown with the expensive resources still running. Until these move to their own state file, take them out of this one first:

```bash
terraform state rm aws_ecr_repository.app aws_ecr_lifecycle_policy.app aws_budgets_budget.monthly
terraform destroy
```

The budget in particular is worth keeping: it costs nothing and keeps watching an account nobody is looking at any more.

Resources whose lifecycle differs from the application's belong in a separate state, the way `bootstrap/` already holds the OIDC provider and CI role. That is the actual fix and it has not been made yet.
